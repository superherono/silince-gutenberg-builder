# Button Variant Generation — contract

**Single source of truth** for generating button variants (color) and sizes from the project's design system. All 3 modes (`create-block`, `convert-react-page`, `convert-html`) and the `/generate-button-variants` command refer here — the logic is not duplicated.

> Related: [css-custom-properties.md](css-custom-properties.md) (token→alias resolution), [button-template-system.md](button-template-system.md) (copying the button template).

---

## What is generated

Button variants (`primary`/`secondary`/`tertiary`/`text` — **the set is defined by the design file, not the plugin**) and the size axis (`small`/`medium`/`large`) are not written by hand. A variant name lives in **4 surfaces at once**, and the generator syncs them all from a single source:

| # | Surface | What is generated |
|---|---|---|
| 1 | `style.scss` | SCSS maps `$button-variants` + `$button-sizes` (values as `var(--alias)`); the generic `@each` loop is already in the template |
| 2 | `block.json` | `attributes.buttonVariant.enum` + `default`; `attributes.buttonSize.enum` |
| 3 | `edit.js` | `SelectControl` options for variant and size |
| 4 | `edit.js` / `save.js` | **conditional** runtime overrides (see §6) — the structure is already in the template and must not be broken |

Any of the 4 out of sync = a bug (a `--primary` class without a rule in SCSS, as happened in the legacy code). Generation always touches all 4.

---

## Inputs

They are read statically (the plugin runs in Claude Code, not in the WP runtime); paths come from `src/.claude/config.json`, relative to the theme root:

1. **`designSystemPath`** — the project's design system markdown. Front-matter YAML, section `components.button-*` — **which variants exist and their recipe** (slot → token). `DESIGN-integroflow.md` in the plugin is a format sample, not data.
2. **`themeJsonPath`** (default `theme.json`) — token **values** and slugs; the validator of whether a token exists.
3. **`themeAliasesPath`** (default `src/scss/variables.scss`) — the alias whitelist (which preset each one points to).

If `designSystemPath` is not set/the file does not exist → see §7 (ask the user — no auto fallback).

## 1. Deriving variant names

Key `components.button-<name>` → variant name `<name>`. Example from the sample:

```yaml
components:
  button-primary:   { backgroundColor: "{colors.primary}", textColor: "{colors.on-primary}", typography: "{typography.button-md}", rounded: "{rounded.md}", padding: "{spacing.md} {spacing.xl}", hoverBackground: "{colors.primary-deep}" }
  button-secondary: { backgroundColor: "{colors.ink}",     textColor: "{colors.on-primary}", ... }
  button-tertiary:  { backgroundColor: "{colors.canvas}",  textColor: "{colors.ink}", borderColor: "{colors.line-strong}", ... }
  button-text:      { backgroundColor: transparent,        textColor: "{colors.primary}", typography: "{typography.button-sm}", padding: "{spacing.sm} {spacing.md}" }
```

→ variants `primary`, `secondary`, `tertiary`, `text`. The first in the list (or `primary`, if present) is `buttonVariant.default`.

---

## 2. Mapping design slots → `--button-*`

The keys of the inner SCSS map **match the CSS variable suffix** (`bg-color` → `--button-bg-color`), so `@each` emits `--button-#{$prop}` without a renaming table.

| Slot `components.button-*` | Map key (= `--button-` suffix) | Note |
|---|---|---|
| `backgroundColor` | `bg-color` | `transparent` → literal |
| `hoverBackground` | `bg-color-hover` | |
| `textColor` | `text-color` | |
| `borderColor` | `border-color` | if present → also `border-width: 1px` |
| `rounded` | `border-radius` | "no pill" design → usually `{rounded.md}` |
| `padding` (2 values) | `padding-y` + `padding-x` | split on the space: 1st→y, 2nd→x |
| `typography` | `font-size` | weight/family/tracking — the block's base defaults (DESIGN: Inter 600) |
| `iconBackground` (opt.) | `icon-bg` | icon chip color |
| `iconColor` (opt.) | `icon-color` | |

A variant lists **only what it overrides**; the rest comes from the base defaults `--button-*` at the block root.

**Behavior flags** (not custom props, handled by `@if` in the loop):
- `underline-hover: true` — text underline on hover (typical for `text`).
- `dark-context: true` — overrides for a light button on dark sections. NOT generated by default; only if the variant declared it.

---

## 3. Resolving tokens `{...}` → `var(--alias)`

**Do not duplicate the table — it is in [css-custom-properties.md](css-custom-properties.md#alias-name-derivation-rules-for-understanding-the-whitelist-is-still-variablesscss).** In short:

| Reference in the design | Alias |
|---|---|
| `{colors.X}` | `var(--X)` (color slug = alias, no prefix) |
| `{colors.accent-gradient}` | `var(--gradient-accent)` (gradient: `--gradient-{slug}`) |
| `{spacing.X}` | `var(--space-X)` |
| `{rounded.X}` | `var(--radius-X)` |
| `{typography.X}` | `var(--text-X)` |
| `transparent` / `0` / `none` | literal |
| `color-mix(... {token} ...)` | pass through, resolving nested references |

**Contract B1:** the value exists in theme.json → `var(--alias)`; no alias in `variables.scss` → hardcode the value from theme.json; not in theme.json at all → literal as is. The color name in the design (`colors.primary`) must match the slug in theme.json — otherwise validate and warn.

---

## 4. Sizes (`small`/`medium`/`large`)

The design usually has **no** size axis — it is the plugin's axis. Default policy (values from theme.json tokens):

| Size | Overrides | Meaning |
|---|---|---|
| `medium` | `()` (empty) | variant default |
| `small` | `font-size: var(--text-button-sm)`, `padding-y: var(--space-sm)`, `padding-x: var(--space-md)` | compact |
| `large` | `padding-y: var(--space-lg)`, `padding-x: var(--space-2xl)` | large |

If `designSystemPath` describes sizes (e.g. `components.button-sizes`) — take them from there; the policy above is only the default.

---

## 5. Output form in `style.scss`

The template contains a generic loop (NOT rewritten). **Only the contents of the two maps** are generated:

```scss
$button-variants: (
	primary: (
		bg-color: var(--primary),
		bg-color-hover: var(--primary-deep),
		text-color: var(--on-primary),
		border-radius: var(--radius-md),
		padding-y: var(--space-md),
		padding-x: var(--space-xl),
		font-size: var(--text-button-md),
	),
	// ... other variants
);

@each $name, $cfg in $button-variants {
	&--#{$name} {
		@each $prop, $val in $cfg {
			@if $prop != 'underline-hover' and $prop != 'dark-context' {
				--button-#{$prop}: #{$val};
			}
		}
		@if map-get($cfg, 'underline-hover') {
			.{namespace}-{block}__link:hover .{namespace}-{block}__text {
				text-decoration: underline;
				text-underline-offset: 4px;
			}
		}
	}
}
```

Rules:
- `map-get()` (NOT `@use 'sass:map'`) — so as not to depend on the build configuration.
- Emit `border-width` only if the variant has `border-color` (otherwise base `0`).
- The loop and the base defaults `--button-*` are generic, shared by all variants; do not duplicate them per variant.

## 6. Conditional runtime overrides (edit.js / save.js)

⚠️ **Without this, the variants are not visible.** An inline `style={{'--button-bg-color': backgroundColor}}` on the root overrides the variant class on the same element. Therefore:

- runtime `--button-*` are emitted **only when the attribute is actually set** (the user picked a color/size/radius); otherwise the key is omitted and the variant class takes over;
- the defaults of `backgroundColor`/`textColor`/`iconBackgroundColor`/`iconColor`/`buttonFontSize` in `block.json` are **empty** (`""`);
- `getBorderRadius()` / `getFontSize()` return `null` when the value is not set.

Color pickers and controls remain as a variant **override**, not as a default.

> The options of the **"Font Size"** control come live from `theme.json` via `useSettings('typography.fontSizes')` (value = `var(--text-{slug})`), narrowed to button roles (`button-*`), and are NOT hardcoded px. This is part of the `edit.js` template, is **not generated** by the command and updates automatically following `theme.json`.

## 7. No design file → ask the user

If `designSystemPath` is **not set** in config OR the file at the given path is **not found** — **DO NOT generate silently and DO NOT fall back automatically**. Ask the user via `AskUserQuestion` what to do. In the question text, state exactly which path was checked (the `designSystemPath` value or "key not set in config"), so that the user immediately notices a typo/misconfiguration.

> If you found a plausible candidate on disk yourself (`DESIGN*.md` in the theme/`temp/`) — **DO NOT use it silently**: offer it as the first option ("Use `<path>` + write it to config?"). The ask trigger is the **state of the key in config** (not set) or a missing file, not "no design file anywhere in the universe".

Answer options:

1. **Specify/confirm the path to the design file** — the found candidate or a path from the user ("Other"); reread it and continue under the normal contract (§1–§6). Offer to add `designSystemPath` to config so that subsequent runs are authoritative.
2. **Generate from the `theme.json` palette** (a generic set without a design file) — the default set from the palette roles: `primary` (`--primary`/`--on-primary`, hover `--primary-deep`), `secondary` (`--ink`), `tertiary` (`--canvas`/`--ink` + border `--line-strong`), `text` (transparent/`--primary`, `underline-hover`). A role is missing from the palette → skip the variant and warn.
3. **Cancel** — do not touch the files, finish without changes.

> The palette set is NO LONGER applied on its own — only if the user explicitly chose it in option 2.

## Finding the button block (discovery)

Search for the button **inside `blocksDir`**, which is resolved from `pluginSettings['silince-gutnebrg-builder'].blocksDir` (default `./blocks`) relative to the **theme root** (the current directory). Order:

0. **Resolve `blocksDir`.** No key in config → default `./blocks`. Everything below is relative to it. ⚠️ If the button lives in `src/blocks/...` but `blocksDir` is left at the default `./blocks` — the search goes to the wrong place and the button "will not be found". `blocksDir` must point to the real blocks folder (e.g. `src/blocks`).
1. **Explicit `block-name`** (argument) → look for `block.json` in order: `{blocksDir}/{name}/`, then `{blocksDir}/common/{name}/`, or the `dir` from the registry for the key `{name}`.
2. **No argument — registry.** Read `{blocksDir}/common/.registry.json`. The `button` role exists AND its `dir` exists on disk → that is the button. The role exists but the folder is not on disk → the registry is stale: **warn, do not generate blindly** (the registry is a hint, the disk is the truth; offer to fix the entry/specify the path).
3. **No registry/role — convention, in order:**
   - a. `{blocksDir}/common/default-button/block.json`
   - b. `{blocksDir}/default-button/block.json`
   - c. recursive scan under `blocksDir` for a `block.json` whose `attributes` contain `buttonVariant` (the structural signature of our button) — catches custom names/locations.
4. **Several candidates** → list them and ask which one (or require `block-name`).
5. **Not found** → **DO NOT create silently.** First check whether the button was **deleted by accident**: if it is not in the working tree but is in `git HEAD` or in `build/blocks/` — this is probably WIP/an accidental deletion; offer **restore from git** as the first option. Otherwise report "button not found under `{blocksDir}`" and offer to scaffold a new `default-button` from `templates/button/` ([button-template-system.md](button-template-system.md); ask for the location — recommended: `common/`). **After the scaffold you MUST run §8 again** — `$button-variants`/`$button-sizes` in the template are only a **skeleton example (integroflow-shaped), NOT authoritative output**: they must be rebuilt from the project's design system, and if `designSystemPath` is not set/not found — go to the §7 ask (DO NOT trust the template maps by default). Scaffold declined → stop, no changes.

> ⚠️ A common trap: on scaffold the template already contains ready-made maps — do not accept them as the generation result. A match with the project's design is guaranteed only for integroflow (whose output is baked into the example). Always regenerate/ask.

**Target validation:** the found block must be compatible (`block.json` has `buttonVariant`/`buttonSize` or style.scss has `$button-variants`). `core/button` or someone else's block → warn that the template is incompatible, do not touch it.

---

## 8. Procedure (idempotent)

1. Find the button block per "[Finding the button block](#finding-the-button-block-discovery)" above. Not found → the behavior from discovery item 5 (scaffold or stop).
2. Read `designSystemPath` (→ variants+recipes), `themeJsonPath` (→ values), `themeAliasesPath` (→ whitelist). `designSystemPath` not set/file not found → **§7 (ask the user)**, do not continue silently.
3. For each `components.button-*`: build the inner map, resolving `{tokens}` per §3, splitting `padding`, setting `border-width`/flags per §2.
4. Build `$button-sizes` per §4.
5. **style.scss** — replace the contents of `$button-variants` and `$button-sizes` (do not touch the loop and structure).
6. **block.json** — `buttonVariant.enum` = variant names, `default` = primary/the first one; `buttonSize.enum` = size names.
7. **edit.js** — `SelectControl` options (variant/size) = the same set (label = Title Case).
8. Check that edit.js/save.js make the runtime overrides conditional (§6) — if not, fix it.
9. Report: which variants/sizes were generated, which tokens did not resolve (if any).

A repeat run = a full rebuild of the 4 surfaces from the current design file.
